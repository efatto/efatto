Helpdesk AI Draft Replies

Prepares draft replies to helpdesk tickets with an AI model, without sending personal data to the model and without anything reaching the customer before a technician approves it.

The module removes the recognisable classes of personal data before anything leaves Odoo: e-mail addresses, phone numbers, IBANs, VAT numbers, Italian fiscal codes, SdI recipient codes, document numbers and URLs, plus every value of the contacts Odoo already knows. It does not prove anonymity: a name that is not stored as a contact, a nickname or a detail that identifies a person by context is not detected, so the technician confirms that they checked the text before sending it.

The flow has two approvals:

  1. Question. The ticket text is pseudonymized in Odoo: names, companies, emails, phone numbers, VAT numbers, Italian fiscal codes, IBANs, SdI recipient codes and document numbers become placeholders such as [PERSON_1] or [EMAIL_1]. The technician checks and completes the question, ticks I checked the question for personal data, then sends it. Sending is blocked while the automatic check still finds a match.
  2. Reply. The draft comes back with the cited sources and a confidence level (high, medium, low). Odoo puts the real data back in place of the placeholders and posts the draft as an internal note. The technician approves, modifies or rejects it; modifying or rejecting requires a reason.

Every review is stored in the draft log to measure precision: the texts are pseudonymized, the technician’s note and the model’s confidence reason are pseudonymized too (they are free text and would otherwise quote what slipped through). The log is an operational record, not an anonymous dataset: do not export it as a training set.

The module also keeps a question and answer archive, the material that extends what the AI can answer:

  • replies approved by a technician enter it automatically (auto_validate_reviewed can be disabled to keep them to validate);
  • a wizard retrieves already solved tickets (question plus staff reply), pseudonymized and to be validated by a manager;
  • each entry is either knowledge base (indexed by the external AI system as a source it can cite) or test set (kept out of the knowledge base and used only to measure precision);
  • validated entries can be exported as JSON Lines, the knowledge base and the test set separately;
  • editing a validated entry sends it back to validation.

The connection to the model goes through the OCA module ai_oca_bridge: Odoo sends the question to an external system (for example n8n or a RAG service), which queries the model and returns the draft.

Configuration

Groups. Give technicians the group Helpdesk AI Assistant / Technician. The Manager group validates the archive, imports solved tickets and manages the review reasons. The draft log is write-once: no group can edit or delete it, so the metrics cannot be changed after the fact.

AI bridge. In AI Bridge create a bridge with:

  • Model: Helpdesk Ticket (helpdesk.ticket)
  • Payload type: Helpdesk: pseudonymized question
  • Result type: Helpdesk: draft reply
  • Result mode (immediate or asynchronous), URL and authentication of the external system

The bridge usage must stay None: the question is sent by the ticket buttons, never automatically (a constraint refuses an automatic usage).

Do not create a bridge with payload type Record on Helpdesk Ticket: that payload sends the fields of the ticket as they are (description, contact, chatter) and defeats the pseudonymization. Use it only on models without personal data.

Odoo sends this payload (plus _odoo and, for asynchronous calls, the _response_url added by ai_oca_bridge). For this payload type the module removes db_name and user_id from _odoo, because the database name is usually the customer’s name: only db (the uuid) and db_hash remain.

{
  "question": "Pseudonymized text approved by the technician",
  "ticket": "TICKET-42",
  "language": "it_IT",
  "odoo": {"version": "18.0", "edition": "community"},
  "installed_modules": ["account", "l10n_it", "l10n_it_edi"],
  "abstention_text": "I have no verified information to answer.",
  "confidence_levels": ["high", "medium", "low"]
}

The external system must reply (immediately or on _response_url) with:

{
  "answer": "Text with the placeholders and the citations [F1]",
  "abstained": false,
  "confidence": "high",
  "confidence_reason": "Every step has a source for version 18",
  "sources": [{"ref": "F1", "title": "Odoo 18 - Italy", "url": "https://..."}],
  "citations_verified": true,
  "retrieval_score": 0.82,
  "model": "model name"
}

When confidence and confidence_reason are missing, the module reads the CONFIDENCE: and REASON: lines (or the Italian AFFIDABILITA: and MOTIVO:) at the end of answer. The final level can only go down: it becomes low when citations_verified is false and drops one step when retrieval_score is below the threshold.

Q&A archive for the AI. The external system can read the validated knowledge base entries in two ways:

  • export them from the archive list (actions Export the knowledge base for the AI (JSONL) and Export the test set (JSONL), which never mix) and load the file into the RAG index;
  • read the model helpdesk.ai.qa through the Odoo API with a dedicated user, filtering state = validated and usage = knowledge.

Never index the test set entries.

System parameters (helpdesk_mgmt_ai.*):

  • abstention_text: fixed text the model uses to abstain. Keep it in the language of the system prompt.
  • min_retrieval_score: threshold on the source score; 0 disables it. Set it after looking at the real scores.
  • test_share_percent: share of new archive entries kept for the test set (default 20).
  • auto_validate_reviewed: True to validate automatically the replies approved by a technician. Off by default: the entry is the material the model cites, so it deserves a second pair of eyes.
  • use_presidio: True to add the recognition of names and places with Microsoft Presidio (requires presidio-analyzer and the spaCy model on the Odoo server). When it is on and the library or the model is missing, sending is blocked instead of silently degrading name detection.
  • presidio_language, presidio_spacy_model, presidio_min_score: Presidio language (it), spaCy model (it_core_news_lg) and minimum entity score (0.6).

Usage

Draft replies

  1. Open a ticket and press Prepare AI draft. The AI Assistant tab shows the pseudonymized question.

  2. Check the question. You can complete it with version, module and error message. Tick I checked the question for personal data and press Approve and send the question. If the automatic check still finds a value, the send is refused and the values are listed in the AI tab. Names that are not stored as a contact in Odoo are not detected: they are what the checkbox is for.

  3. When the draft is ready, it appears as an internal note with its confidence level. Press Review AI draft and choose:

    • Approved as is: the reply is sent as it is;
    • Modified: correct the text and select a reason;
    • Rejected: select a reason; nothing is sent to the customer.

    Changing the text of a draft marked as approved counts as modified and requires a reason. The reasons Other and Personal data slipped through require a note. Any placeholder left in the reply ([PERSON_1], known or not) blocks the send: replace it with the real text by hand.

Q&A archive

  1. In AI Assistant / Configuration / Import Solved Tickets choose period, teams, categories and whether to take the last staff reply or all of them. Tickets already in the archive are skipped.
  2. In AI Assistant / Q&A Archive check each imported entry: correct the text if needed, set the usage (knowledge base or test set) and press Validate. Entries that may still contain personal data cannot be validated; editing a validated entry sends it back to validation.
  3. Select the validated entries and run Export the knowledge base for the AI (JSONL) to update the RAG index. The test set has its own action and is never indexed.

Metrics

In AI Assistant / Draft Log the pivot view shows the outcomes by confidence level: it checks that the level declared by the model is reliable.

Known issues / Roadmap

  • Pseudonymization is not perfect: a name that is not stored as a contact, a misspelled name, a nickname or a detail that identifies a person by context can slip through. The automatic check covers formats (e-mail, phone, IBAN, VAT, fiscal code, SdI code, document numbers, URLs), values of known contacts, a leftover @, runs of 9+ digits and query strings; the technician confirms the rest with a checkbox.
  • The archive keeps [PERSON_1] numbering per entry, so two entries about the same person can share a placeholder: add a per-entry suffix if the archive is ever shared outside the company.
  • Ticket attachments are not sent.
  • Only the initial ticket text (subject and description) is used, not the following messages.
  • Automatic sync of the validated archive with the RAG index, instead of the JSONL export.
